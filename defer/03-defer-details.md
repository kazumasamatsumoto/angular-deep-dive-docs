# 塊の記録：TDeferBlockDetails と LDeferBlockDetails の欄

> interfaces.ts の TDeferBlockDetails（loadingState・dependencyResolverFn・loadingPromise・各テンプレートの番号・placeholderBlockConfig・loadingBlockConfig・flags）と LDeferBlockDetails（今の状態・トリガーの後片付け・state の予定）、DeferBlockState と DeferBlockInternalState の違い、utils.ts の getTemplateIndexForState・getMinimumDurationForState などの読み出し。

---

`@defer` の塊 1 つには、TView の側の `TDeferBlockDetails`（テンプレートに 1 つ）と LView の側の `LDeferBlockDetails`（描いた塊ごとに 1 つ）の 2 つの記録があります。この章では、その欄を `interfaces.ts` の実物の行で 1 つずつ確かめ、`utils.ts` の読み書きの関数と、状態の番号 `DeferBlockState` と `DeferBlockInternalState` の違いを読みます。デモでは、形の違う 4 つの塊の記録を並べて、欄の値がテンプレートのどこから来たかを対応させます。

読む対象は `packages/core/src/defer/interfaces.ts`・`utils.ts` と、`rendering.ts` の先頭のトークンの宣言です。

- **19〜23 行目 `DehydratedDeferBlock`**：塊を 1 つ指すための `{lView, tNode, lContainer}` の 3 つ組です。「塊のある LView」「塊の TNode」「塊のスロットの LContainer」がそろえば、2 つの記録も（TNode の番号 + 1 で）引けます。ハイドレーションの登録簿と、テスト用の `getDeferBlocks` の結果がこの形です。

## 3. 状態の番号：DeferBlockState と DeferBlockInternalState

公開の `DeferBlockState`（Placeholder 0・Loading 1・Complete 2・Error 3）は [defer の章](../template/03-defer.md)で引用しています。もう 1 つの、公開されていない番号がこれです。

📄 `angular/packages/core/src/defer/interfaces.ts` L206–230 （▶ の行: 207, 213, 219, 224–225, 227, 229）

```ts
206 │ /** Describes specified delay (in ms) in the `hydrate on timer()` trigger. */
207 ▶ export interface HydrateTimerTriggerDetails {
208 │   type: DeferBlockTrigger.Timer;
209 │   delay?: number;
210 │ }
211 │ 
212 │ /** Describes the config for a `hydrate on viewport` trigger. */
213 ▶ export interface HydrateViewportTriggerDetails {
214 │   type: DeferBlockTrigger.Viewport;
215 │   intersectionObserverOptions?: IntersectionObserverInit;
216 │ }
217 │ 
218 │ /** * Describes all possible hydration trigger details specified in a template. */
219 ▶ export type HydrateTriggerDetails = HydrateTimerTriggerDetails | HydrateViewportTriggerDetails;
220 │ 
221 │ /**
222 │  * Describes the initial state of this defer block instance.
223 │  *
224 ▶  * Note: this state is internal only and *must* be represented
225 ▶  * with a number lower than any value in the `DeferBlockState` enum.
226 │  */
227 ▶ export enum DeferBlockInternalState {
228 │   /** Initial state. Nothing is rendered yet. */
229 ▶   Initial = -1,
230 │ }
```

207〜219 行目は、2 節の `hydrateTriggers` の値の型です（timer の遅れと viewport の IntersectionObserver の設定だけが詳細を持つ）。227〜230 行目の `DeferBlockInternalState.Initial` は **-1** で、「まだ何も描いていない」です。224〜225 行目の注意書きのとおり、この値は `DeferBlockState` のどれよりも小さくなければいけません。状態を変えてよいかの判定が「今の値 &lt; 新しい値」という数の比べ方だからです（[第 4 回](04-defer-render-state.md)の `isValidStateChange`）。-1 なら、Placeholder（0）にも、placeholder を飛ばして Loading（1）や Complete（2）にも進めます。

`Initial` を公開の enum に入れないのは、テストで `DeferBlockFixture.render(state)` に渡せる値（描ける状態）と、実行時の「何も描いていない」を分けておくためです。`@placeholder` が無い塊は、トリガーが発火するまでずっと `Initial` です（5 節のデモの塊 3・4）。

## 5. DEMO：形の違う 4 つの塊の記録（記録の再生）

> **🧪 DEMO — 欄の値はテンプレートのどこから来るか（記録の再生）**
>
> これは記録です。本物の @angular/core 22.1.6（開発モード・JIT）を Node で、domino の DOM の上で動かした結果です。アプリには下の表の 4 つの塊を並べ、4 つとも `when go()` を持たせて、`go.set(true)` で同時に発火させます。JIT では本来の「依存を読み込む関数」が null なので、`ɵDEFER_BLOCK_DEPENDENCY_INTERCEPTOR` で「30ms 後に解決する Promise を返す関数」に差し替えています（7 節）。`STATE_IS_FROZEN_UNTIL` は時刻そのものに意味が無いので、記録した時刻からの残りの ms に直して記録しました。共通の部品の全文は [第 1 回](01-defer-overview.md)にあります。
>
> LView の側（LDeferBlockDetails）を段ごとに見ます。
>
> 「次の段へ」か段のボタンを押してください。
>
> ▶ [このデモはサイトで動かせます](https://angular-deep-dive-cyan.vercel.app/chapter/defer-details)

記録から読み取れることです。

1. **TView の側：テンプレートの番号は「本体 → @loading → @placeholder → @error」の順に振られる**

   塊 2 は本体 4・@loading 5・@placeholder 6 です。コンパイラが本体・Loading・Placeholder・Error の順にビューを作るので（[compiler-control-flow-phases の章](../compiler/15-compiler-control-flow-phases.md)の `ingestDeferBlock`）、番号はいつもこの順に振られます（[第 2 回](02-defer-instruction.md)の例も 2・3・4・5）。塊の TNode の番号（29・34・38・41）は、各塊が使うスロットの数（状態の数 + 2）ずつ進みます。値は 22.1.6 の `HEADER_OFFSET` 27 を含みます。`@placeholder (minimum 500ms)` は `[500]`、`@loading (after 100ms; minimum 1s)` は `[1000, 100]`（minimum が先）です。`debug` は塊 2 だけ `on timer(5000ms)` と `when <expression>` の 2 つです。
2. **段 1：@placeholder の無い塊 3・4 は `Initial`**

   トリガーの命令は placeholder を描こうとしますが、描くテンプレートが無いので状態は -1 のままです。塊 1 は placeholder を描いた時点で `minimum 500ms` が始まり、`STATE_IS_FROZEN_UNTIL` に「500ms 後」が入っています。`TRIGGER_CLEANUP_FNS` は塊 2 だけ 2 つ（`ɵɵdefer` の 1 つ + タイマーを止める 1 つ）です。
3. **段 2：発火したら 4 つとも `TRIGGER_CLEANUP_FNS` が null、`loadingState` は IN\_PROGRESS**

   発火のときに後片付けが全部呼ばれて、欄が null に戻ります（塊 2 の 5 秒のタイマーもここで止まる）。塊 1 は minimum の途中なので Loading を描けず、`NEXT_DEFER_BLOCK_STATE` に Loading が入ります。塊 2 は `after 100ms` の間待つので、`LOADING_AFTER_CLEANUP_FN` に関数が入り、やはり `NEXT` は Loading です。塊 3・4 は @loading が無いので `Initial` のままです。
4. **段 3：読み込み（30ms）が終わると、塊 2・3・4 は Complete、塊 1 はまだ Placeholder**

   塊 2 は 100ms を待つ前に読み込みが終わったので、Loading を一度も描かずに Complete になり、`LOADING_AFTER_CLEANUP_FN` と `NEXT` が null に戻りました。塊 3・4 は `Initial`（-1）から Complete（2）へ直接進んでいます。塊 1 は minimum が残っているので、`NEXT` が Complete に書き換わって待っています。
5. **段 5：minimum が過ぎると塊 1 も Complete**

   タイマーが `NEXT` の状態を描き、`NEXT` と `STATE_IS_FROZEN_UNTIL` を null にしました。この時間の仕組みは [第 5 回](05-defer-minimum-after.md)で 1 行ずつ読みます。

## 聞かれそうな質問

**Q. TDeferBlockDetails と LDeferBlockDetails は、どう使い分けられているのですか？**

同じテンプレートのすべてのインスタンスで同じものが TView の側（各状態のテンプレートの番号・設定・依存の関数と読み込みの進み具合、interfaces.ts 83〜157 行目）、インスタンスごとに違うものが LView の側（今の状態・タイマー・トリガーの後片付け、254〜307 行目）です。どちらも塊のスロットの次の番号に置かれます（utils.ts 52・70 行目）。

**Q. なぜ LView の側の記録はオブジェクトではなく配列なのですか？**

LView 自体が配列で、そのスロットに置かれるからです。233〜236 行目のとおり、スロットを見ていく処理は 1 番目の値で LView か LContainer かを見分けるので、記録の 1 番目（`DEFER_BLOCK_STATE`）を必ず数にしておけば取り違えられません。

**Q. `Initial`（-1）は、いつ見えますか？**

`ɵɵdefer` の直後と、@placeholder の無い塊がトリガーを待っている間です。デモの段 1〜2 の塊 3・4 がそうでした。数が Placeholder（0）より小さいので、そこから どの状態へも進めます（224〜225 行目）。

**Q. @loading を書いたのに、Loading が一度も描かれないことはありますか？**

あります。`after` を付けていて、その時間より早く読み込みが終わった場合です。デモの塊 2（`after 100ms`）は 30ms で読み込みが終わり、Loading を描かずに Complete になりました。`LOADING_AFTER_CLEANUP_FN`（276 行目）がそのタイマーを止める関数です（[第 5 回](05-defer-minimum-after.md)）。

**Q. 本番のビルドでも `debug.triggers` は埋まりますか？**

埋まりません。`trackTriggerForDebugging`（191 行目）を呼ぶのは、トリガーの命令の `if (ngDevMode)` の中だけです。だから DevTools のトリガーの表示も開発モードだけです。

## 読み終えて

- TView の側（`TDeferBlockDetails`）は各状態のテンプレートの番号・minimum と after の設定・依存の関数・読み込みの進み具合・providers・flags・debug を持つ。
- LView の側（`LDeferBlockDetails`）は 10 個の欄の配列で、今の状態・次の状態・minimum の期限・after のタイマー・3 系統のトリガーの後片付け・SSR の id と状態・完了のときの関数を持つ。
- 状態は公開の 0〜3 と内部の `Initial`（-1）。-1 はどの状態よりも小さいので、placeholder が無い塊はそこから直接 Complete に進める。
- `utils.ts` は「スロットの番号 + 1」で 2 つの記録を読み書きし、状態からテンプレートの番号を引く。null なら描かない。
