# テンプレート参照（#ref）と pipe の型

> #ref が要素・ディレクティブ・TemplateRef のどれを指すかを TcbReferenceOp が決める行、checkTypeOfDomReferences と checkTypeOfNonDomReferences、exportAs。pipe の呼び出しを pipeInst の transform として書く仕組み、checkTypeOfPipes が偽のとき、pipe の宣言が見つからないときの診断。

## 1. #ref の行き先は誰が決めるか

`#ref` がどのノード・どのディレクティブを指すかは、型チェックの前に R3TargetBinder が決めています（[テンプレートコンパイラ第 9 回](../compiler/09-compiler-binder.md)で引用済みの t2\_binder.ts）。規則は 3 つです。

- `#ref` に値が無い：要素にコンポーネントが付いていればそのコンポーネント、無ければ要素そのもの（`<ng-template>` なら Template）。
- `#ref="name"`：その要素のディレクティブのうち `exportAs` に `name` を含むもの。
- どれも無い：行き先なし（`null`）。

Scope は要素・Template などを足すたびに `checkAndAppendReferencesOfNode` を呼び、`getReferenceTarget(ref)` の結果で op を選びます。行き先が無ければ `missingReferenceTarget` を帯域外の診断（TypeScript を通さず Angular が直接出す診断。[第 17 回](17-typecheck-oob.md)）に記録して `TcbInvalidReferenceOp`、要素か Template なら `TcbReferenceOp(target)`、ディレクティブなら `TcbReferenceOp(target.directive)` を積みます。この関数は第 9 回で引用済み（scope.ts の `checkAndAppendReferencesOfNode`）なので、ここでは積まれた op の中身を読みます。

## 4. 宣言の前で読む・ブロックの外から読む

デモの「宣言の前・ブロックの外から読む」は、次の結果になります（位置のコメントを消したもの）。

- `var _t2 = document.createElement("input");` — `<input #box>` は後ろにあるのに、先頭に出る
- `var _t1 = _t2;` — `box`
- `"" + (_t1).value;` — テンプレートの先頭の `{{ box.value }}`
- `if ((this).show) { "" + ((_t1)).value; }` — `@if` の中からも同じ `_t1`
- `"" + (this).inner;` — **コンポーネントのプロパティ**として読まれる

宣言の前で読めるのは、`TcbReferenceOp` が optional で、読まれた時点で実行される（op を遅れて実行する仕組みは[第 6 回](06-typecheck-scope.md)）からです。`@if` の中の子の Scope は、自分に無い参照を親の Scope に尋ねます。逆に、`@if` の中で宣言した `#inner` は外の Scope から見えません。binder がテンプレートの名前として解決しないので、上の並びの最後は `this.inner` になり、コンポーネントに `inner` が無ければ「Property 'inner' does not exist on type …」という TypeScript のエラーになります。参照のエラーではない点に注意してください。

   関数を `any` にするので、引数の型も戻り値の型も見ません。ただし引数の**式そのもの**（`(this).total` など）は訳されたまま残るので、存在しないプロパティのエラーは出続けます。`strictTemplates` が偽なら偽になる設定です（[第 2 回](02-typecheck-config.md)）。

## 聞かれそうな質問

**Q. #ref の型はどう決まりますか？**

行き先は binder が決め（値なしならコンポーネントか要素、値ありなら `exportAs`）、型は references.ts 73〜76 行目で行き先の変数をそのまま使います。要素なら `document.createElement("input")` の型（`HTMLInputElement`）、ディレクティブならインスタンスの型、`<ng-template>` なら 93 行目で `TemplateRef<any>` です。

**Q. exportAs を打ち間違えるとどうなりますか？**

帯域外の診断「No directive found with exportAs '…'」が 1 つ出て（template\_typecheck\_spec.ts 1879〜1881 行目）、参照そのものは references.ts 121 行目の `null! as any` になります。そのため参照を使った式の型エラーは出ません（1857 行目の it）。

**Q. @if の中で宣言した #ref を外で使うとどうなりますか？**

外の Scope からは見えないので、binder はテンプレートの名前として解決せず、TCB では `(this).inner` というコンポーネントのプロパティの読み取りになります（4 節のデモ）。コンポーネントにその名前が無ければ TypeScript の「Property does not exist」になり、参照のエラーにはなりません。

**Q. pipe の型チェックは何を見ていますか？**

pipe のクラスの `transform` メソッドの宣言です。ops/expression.ts 228 行目で `_pipe1.transform(左辺, 引数…)` という普通の関数呼び出しにし、`_pipe1` は environment.ts 112 行目の `null! as i0.DatePipe` なので、引数と戻り値の型を TypeScript が検査します。`checkTypeOfPipes` が偽なら 225 行目で関数を `any` にします。

**Q. 知らない pipe を書くと、その行の他のエラーは出なくなりますか？**

出ます。ops/expression.ts 189 行目で pipe を `(0 as any)` にするだけで、181 行目で訳した左辺や引数の式は残ります（188 行目のコメント「残りの式を検査できるように」）。手元の結果では、`total | nopipe` で帯域外の `missingPipe` と `total` の TS2339 の両方が出ました。

## 読み終えて

- `#ref` の行き先は binder が決め、TCB では `var _t1 = 行き先の変数` の 1 行（読まれたときだけ）。`<ng-template>` は `TemplateRef<any>` 固定で、`T` を付けるのは TODO のまま。
- 行き先の無い参照は帯域外の診断を 1 つ出し、TCB では `any`。後続の型エラーは出ない。
- 2 つの参照の設定は `as any` を付けるだけ。コードは「DOM 以外を切ると DOM も any」になっていて、コメントと食い違う（利用者の設定からは到達しない）。
- pipe は `_pipe1.transform(…)` の関数呼び出しで、型は pipe の宣言から TypeScript が決める。宣言は `pipeInst` が TCB の外に 1 回だけ置く。
- 知らない pipe・`@defer` の外の deferred な pipe は `(0 as any)` にして、式の残りの検査は続ける。
